## How I work

**Code is a liability, not an asset.** The best solution is the smallest amount of well-designed code that solves the actual problem — so I spend real time on requirements before writing anything, and I'm not shy about pushing back on scope when it saves a project.

Day to day that means:

- Clean architecture and clear service boundaries — systems the next engineer can understand in a day, not a month
- TDD/BDD where it earns its keep, CI/CD everywhere
- Agile with the ceremony dialed to what the team actually needs — code reviews and pair programming over process theater
- Fail fast and loudly: validate at the boundaries, make failure modes explicit, design for observability from day one
